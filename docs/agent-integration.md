# エージェント連携の調査と設計案

調査日: 2026-09-20

公式資料とローカルCLIのバージョン・ヘルプを確認した調査記録。続くローカル試作で一部の実機検証を実施した結果は [試作の検証結果](prototype-validation.md) を参照。以下の「設計案」はTobari側の提案であり、CLIの提供機能や確定済み要件とは区別する。

## 確認できたこと

### Codex

公式に `SessionStart`、`UserPromptSubmit`、`PermissionRequest`、`Stop`、`Interrupt`、`SessionEnd`、`SubagentStart`、`SubagentStop` とツール前後のhookがある。`Stop` は最終メッセージを受け取れる。サブエージェントhookの `session_id` は親のIDで、`agent_id` を別途扱う必要がある。起動時などに追加コンテキストを渡せる。hookは信頼の確認が必要で、ログファイル形式は安定したインターフェースではない。

出典: [OpenAI公式 Hooks](https://learn.chatgpt.com/docs/hooks)

### Claude Code

セッション・ターン・サブエージェント・ツールのhookがあり、`Stop` は最終メッセージを受け取れるが、ユーザー中断では発火しない。APIエラーには `StopFailure` がある。`TeammateIdle`、`TaskCreated`、`TaskCompleted` も取得候補。ただし `TaskCompleted` の対象はClaude内部の作業項目である。`team_name` は非推奨。`SubagentHandback` 利用時には、終了メッセージと親への報告本文が異なるため注意が必要。

出典: [Claude Code公式 Hooks reference](https://code.claude.com/docs/en/hooks)

### Agent Teams

リードとメンバーは別の実行主体として扱われる。チーム設定にメンバー名やIDがあり、セッション終了でチーム設定が削除される。メンバーはリードの会話履歴を引き継がず、Taskツールを使わずメッセージで調整する場合もある。全てのチームで内部タスクイベントが揃う前提にはできない。

出典: [Claude Code公式 Agent Teams](https://code.claude.com/docs/en/agent-teams)

### ローカル環境

- `codex --version`: `codex-cli 0.155.1`
- `claude --version`: `2.1.276 (Claude Code)`
- Claudeのヘルプで `--name`（表示名・ターミナルタイトル）、`--session-id`、`--settings`、`--append-system-prompt` を確認。
- Codexのヘルプで `--config`、`--cd`、`resume` を確認。同等の起動時命名オプションは今回のヘルプでは確認できなかった。
- ユーザー設定、認証情報、会話ログは読んでおらず、設定変更やモデル呼び出しも行っていない。

## 推奨する連携方式（設計案）

起動ラッパー、CLI別hookアダプター、共通の報告コマンドを組み合わせる。

1. ダッシュボードで発行した起動コマンドをラッパーが受け取り、タスク・作業先・表示名を取得する。
2. ラッパーが起動単位のIDを発行し、CLIを起動する。`SessionStart` で実際のCLIセッションIDと紐づける。
3. hookアダプターが稼働イベントをローカルで必要項目だけに絞り、送信キューへ記録する。
4. 起動時に報告ルールをエージェントへ渡し、節目で共通の報告コマンドを呼ばせる。
5. ローカル送信処理がイベントと報告をバックエンドへ送り、ダッシュボードが表示する。

コマンド名は `tobari start` / `tobari report` とし、後続の試作ではローカルCLIとSQLite受信先を実装した。クラウドAPIは未実装。MCPツールとの比較も未実施。

hookは「動いた・止まった」を観測し、報告は「目的に対してどこまで進んだか」を伝える。最終回答を毎回別のLLMで要約する構成は初版の必須にしない。報告漏れを成功や完了として扱わず、報告未取得と表示する。

## 報告の最小構造（設計案）

| 項目 | 内容 |
| --- | --- |
| 対象 | サーバー側で紐づけたタスク、報告者、タスク全体か担当分か |
| 状態 | 進行中・人の判断待ち・障害で停止・完了 |
| 一言 | 到達点と残件。例「修正とテスト完了。既知の制約を結果欄に記載」 |
| 結論 | 得られた成果・分かったこと |
| 判断根拠 | 採用した基準、理由、主要なトレードオフ。内部思考の逐語記録は不要 |
| 確認結果 | テスト等の結果と成果物参照。未実施・確認不能も明記 |
| 残件 | 未完了事項、制約、阻害要因 |
| 人への依頼 | 判断してほしいことと選択肢。不要なら空 |

全項目を毎回長文で埋める必要はない。中間報告は状態・一言を中心に、判断待ちと完了時には結論・根拠・確認結果・残件を揃える。発生時刻、受信時刻、イベントID、報告リビジョンは連携側で付ける。

報告タイミングは、依頼の理解・方針が定まった時、主要な到達点に達した時、人の判断が必要になった時、作業完了時とする。hookごとの生成や、時間経過だけによる進捗率の推定は不要。

## 状態と識別の扱い（設計案）

- タスクの進行状況とセッションの稼働状態を別々に保存する。登録・起動だけでは作業開始や進捗を断定しない。
- `Stop` のみなら「応答終了・完了報告なし」。有効な取りまとめ役の明示報告を受けて初めてタスクを完了にする。
- `PermissionRequest` は許可確認の兆候。別hookなどによる自動処理もあり得るため、確実な人待ちの判定方法を実機で確認する。
- 完了後の入力送信はセッション稼働の再開として扱う。タスクを再開するかは、その入力が追加作業か単なる質問かをエージェントの報告で区別する。
- サブエージェントの終了や内部タスクの完了は、担当分のイベントとして保存する。全体の完了を更新できる報告者は主セッション／リードに限定する。
- TobariのタスクID、CLI内部タスクID、CLIセッションID、エージェントIDを別フィールドにする。内部IDには提供元と親セッションのスコープを付ける。
- チーム所属と親子関係は分ける。チーム名の文字列だけを永続的な識別子にしない。
- 環境変数は起動時の紐づけに使い、その後はセッションの紐づけ履歴を参照する。タスク切り替えにはリビジョンを付け、遅延イベントを切り替え先へ誤配分しない。
- hookが実行されなかった場合や強制終了では状態が不明になり得る。最終更新時刻と観測欠落を表示し、沈黙から完了を推測しない。

## 送信と時間計測（設計案）

- 生のhook入力にはプロンプトやコマンド出力が入り得るため、そのまま外部へ転送しない。許可した項目と明示的な報告だけを送る。
- hook内で長いネットワーク待ちをせず、ローカルキューと再送を使う。通信失敗がCLI作業を止めない設計にする。
- イベントIDで重複を排除し、順序逆転した古い報告で新しい状態を上書きしない。送信用の秘密はコピー用コマンドに含めない。
- 稼働時間は観測できた作業区間に基づく推定値。LLMが実際に計算した時間とは呼ばない。親が子を待つ区間、入力待ち、欠落区間の定義が必要。
- タスクの経過時間、セッションごとの区間の合計、同時稼働数を区別し、観測が不十分なら不完全な値と分かるようにする。

## 実機試作で確認すべき項目

| ケース | 合格条件 |
| --- | --- |
| 新規起動・再開・コンテキスト圧縮 | 同じ作業を重複登録せず、紐づけと報告ルールを維持 |
| 両CLIのサブエージェント | 親と子を区別し、子の終了でタスクを完了にしない |
| Agent Teamsの各表示モード | メンバーID・リード・担当の対応を確認。取得できない状態は不明と表示 |
| 報告コマンド呼び出し | サンドボックス・環境変数の制約下でも報告者を識別できる |
| 許可確認・質問・中断・APIエラー | 待ち・応答終了・異常を誤って完了にしない |
| 強制終了・ネットワーク断・再送 | 観測欠落を示し、重複や古い報告で表示が壊れない |
| タスク切り替え・セッション再開 | 元の履歴を保持し、イベントを正しいタスクへ関連づける |
| 名前とターミナルタイトル | 対応ターミナルでダッシュボードとの照合ができる |

次の実装検証は、クラウドや画面より先に、ローカル受信先へ「主セッション登録→進捗報告→分担→完了」を通す小さな試作とする。公式仕様の確認は済んだが、最低対応バージョンと実際の発火保証はこの試作後に確定する。
